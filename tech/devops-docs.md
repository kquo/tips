## Devops Documentation

All technical documentation falls into one of four groups, a scheme I take from the [Divio documentation system](https://docs.divio.com/documentation-system/), which I first saw on [Hacker News](https://news.ycombinator.com/item?id=26002656):

1. **Tutorials**: learning oriented.
2. **How-to guides**: problem oriented.
3. **Technical reference**: information oriented.
4. **Explanation**: understanding oriented.

They form a quadrant, drawn on the Divio page, in which each group resembles its two neighbors: tutorials and how-to guides both describe practical steps; how-to guides and reference are both what we need at work, coding; reference and explanation both deal in theoretical knowledge; tutorials and explanation are both most useful when studying rather than working. Recognizing the breakdown adds structure to any documentation.

A few other pointers I keep. One Hacker News comment recommended the SEE method: Statement, Example, Explanation. An Introduction, a Summary, and a Rationale that names the alternatives make a document useful. And [Steven Pinker](../mind/pinker.md)'s point about why there is so much bad writing, the [curse of knowledge](https://en.wikipedia.org/wiki/Curse_of_knowledge): knowing so much about a subject that you forget your readers do not. Finally, be concise.
